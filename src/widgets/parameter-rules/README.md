# Правила параметров: локальный API

Модуль использует существующий RTK Query: два независимых GET и три mutation.
Реальные HTTP-запросы пока не выполняются: queryFn вызывает сервис в памяти с задержкой 350 мс.
Перезагрузка страницы сбрасывает данные и счётчики запросов.

## Временный флаг управления правилами

Внутри компонента `ui/ParameterEditorModal/ParameterRulesFeature.tsx` переключить `parameterRulesEnabled`:

- `false` (по умолчанию) — в редакторе доступны значение по умолчанию и его сохранение; вместо поиска, добавления и списка правил показан блок «Управление правилами в разработке». Удаление всех правил и восстановление удалённых правил также скрыты.
- `true` — полный текущий интерфейс управления правилами.

Флаг меняется в исходниках: dev-сервер подхватит изменение, для production нужна пересборка.
Существующие правила сохраняются при изменении значения по умолчанию.

Когда ограничение больше не нужно, убрать все три обёртки `<ParameterRulesFeature>`
из `ParameterEditorModal.tsx` и `ParameterEditorForm.tsx`, оставив их содержимое.
Удалить `fallback` с информационным блоком, импорты обёртки и неиспользуемый импорт `Alert`
из формы. Затем удалить `ui/ParameterEditorModal/ParameterRulesFeature.tsx`
и этот раздел инструкции.

## Контракты и сохранение

- Типы транспорта: api/contracts.ts. Преобразование GET: api/parameterRulesAdapter.ts.
- GET rules-by-param группирует правила по контексту: `parameters_tech_id`, `journals_tech_id`, `aggregation_levels_tech_id`, `aggregation_rules_tech_id`, `plan_types_tech_id` находятся на верхнем уровне. Вложенные `rules` содержат только поля самого правила; `value` — строка или число. Адаптер преобразует его в число для редактора; пустая строка даёт `NaN`. `scales_tech_id` необязателен и допускает `null`.
- Ключ конфигурации создаёт существующий `getParameterSelectionKey`: `[parameterId, planTypeId, aggregationRuleId, aggregationLevelId, shift?.id ?? null]`. Журнал в ключ не входит; изоляция по журналу остаётся на уровне API. Необязательная смена передаётся вложенным объектом `shift` с `id`; отдельного `shift_id` нет. Отсутствие смены и `null` равнозначны.
- Таблица, счётчики выбора, редактор и загрузка после сохранения используют `selectionKey`. `id` строки и `parameterId` остаются исходным UUID параметра, который отправляется в API.
- POST сохраняет прежний контракт без смены. В моках смена восстанавливается из записи справочника, совпавшей по UUID параметра, типу плана и агрегациям. Если такие записи различаются только сменой, POST отклоняется как неоднозначный, чтобы не сохранить данные в соседнюю конфигурацию. PUT/DELETE адресуют конкретные правила по их ID.
- Функции и свойства берутся из справочников. Названия функций в моках — символы сравнения.
- GET параметра возвращает `default_rule: { id: string, value: number } | null`. `null` означает отсутствие значения по умолчанию.
- Изменённое значение по умолчанию отправляется в `parameter_rules` общего PUT как `{ rules_tech_id: default_rule.id, value: number }`. Если есть PUT обычного правила, запись добавляется в тот же массив. Неизменённое значение не отправляется.
- Очистка значения по умолчанию отправляет его ID в `parameter_rules` общего DELETE. `value: null` в PUT не используется.
- Новое значение по умолчанию отправляется отдельной записью в `parameter_rules` общего POST: `{ name: "Значение по умолчанию", parameters_tech_id, journals_tech_id, aggregation_levels_tech_id, aggregation_rules_tech_id, plan_types_tech_id, created_by, default_value: number }`. Три ID агрегаций и типа плана берутся из выбранного параметра, независимо от наличия обычных правил. Без них создание default блокируется с ошибкой у его поля; изменение и удаление существующего default их не требуют. Наличие обычных правил без default не меняет операцию: используется POST.
- Новые условия, default и дочерние сущности существующих условий объединяются в один атомарный POST. Обычное условие и default передаются разными элементами массива `parameter_rules`.
- DELETE и PUT обычных сущностей отправляются по одной сущности; default-правило может входить в PUT вместе с обычным. Очередь выполняется в порядке DELETE → PUT → POST.
- Ошибка останавливает очередь. Оба GET обновляют исходное состояние, целевой черновик сохраняет оставшиеся правки.
- Ошибки создания, изменения и удаления default-правила отображаются у поля «Значение по умолчанию».
- Параметр может содержать только значение по умолчанию, только обычные условия или оба варианта. Создание пустой конфигурации запрещено; удаление всех существующих правил разрешено. Ноль является заданным default. POST остаётся последней операцией очереди.
- «Удалить все правила» удаляет обычные правила вместе с оформлением и уведомлениями, а также значение по умолчанию. Кнопка доступна и для параметра, у которого сохранено только значение по умолчанию.
- Несохранённые новые правила отмечены тегом «Новое», изменённые существующие — «Изменено». После сохранения теги исчезают. Поле значения по умолчанию не содержит тегов.
- Ошибка синхронизации блокирует запись. Повтор загрузки вызывает только GET.
- Неопределённый результат POST блокирует повторное создание. После загрузки пользователь проверяет серверное состояние, закрыв форму.
- После сбоя GET переоткрытие редактора запрещено до успешного обновления обоих запросов.
- Все технические UUID статические, включая конечный резерв создаваемых записей.
- Демонстрационные ключи Color и Font-weight не являются подтверждением ключей реального API.

## Ручные сценарии ошибок

Открыть /features/antd-table с параметром rulesFault. Каждый сценарий начинает новую сессию моков после полной загрузки страницы.

| Значение                | Результат                                                                     |
| ----------------------- | ----------------------------------------------------------------------------- |
| default-post-rejected   | Первый POST отклонён; при создании только default ошибка показана у его поля  |
| default-put-rejected    | Первый PUT отклонён; при изменении только default ошибка показана у его поля  |
| default-delete-rejected | Первый DELETE отклонён; при очистке только default ошибка показана у его поля |
| partial-put             | Второй PUT отклонён; первый сохраняется                                       |
| partial-delete          | Второй DELETE отклонён; первый сохраняется                                    |
| post-rejected           | Первый POST отклонён целиком, ошибка привязана к имени первого нового правила |
| post-unknown            | Первый POST выполнен, но его ответ потерян                                    |
| refresh-failed          | Вторые запросы обоих GET отклонены; повторные GET успешны                     |
| catalogs-failed         | Первый GET справочников отклонён                                              |
| rules-failed            | Первый GET правил отклонён                                                    |

Дополнительная настройка через localStorage['parameter-rules-faults']:

```json
{ "put": { "call": 2, "mode": "reject", "loc": ["ui_rules", 0, "value"] } }
```

Без call ошибка возникает на каждом запросе соответствующей операции.
mode: unknown имитирует потерю ответа после применения записи.
Для отключения удалить ключ localStorage и перезагрузить страницу.

Для ошибки сохранения только значения по умолчанию:

```json
{ "put": { "call": 1, "loc": ["parameter_rules", 0, "value"] } }
```

Для ошибки очистки значения по умолчанию:

```json
{ "delete": { "call": 1, "loc": ["parameter_rules", 0] } }
```

## Допущения до реального подключения

Уведомление при создании содержит текст и описание без канала/получателей.
Существующие канал и получатели сохраняются.
Шкалы не редактируются. PUT/DELETE возвращают null в моках, POST — строку ok.
Схемы необязательных полей и ответы PUT/DELETE необходимо сверить с реальным сервером.

## Проверки

В моках есть несколько комбинаций «Температуры подшипника» с одним UUID: факт со сменой и обычным правилом, план без смены только с default и максимум со сменой без сохранённой конфигурации. Проверить независимые счётчики, открытие из таблицы и выбора, создание в пустой комбинации, изменение/удаление default и синхронизацию после удаления последней записи. Изменение одной комбинации не должно менять остальные.

Автотесты не добавляются согласно AGENTS.md. Проверки: npm.cmd run build, npm.cmd run lint, npx.cmd tsc --noEmit и браузер.
